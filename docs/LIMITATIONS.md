# 局限与注意事项（必读）

这份文档记录**这个工具不能做什么**，以及与它相关的方法论风险。
写代码的人容易过度自信，所以把局限单独列出来。

---

## 1. 最重要的：指标衡量「内部健康」，不是「输出质量」

**★★★ 这是最容易误用的地方。**

实测：TGAI NB V2.7 在残差范数 ×662、深层几乎全是 BOS sink 的情况下，
仍然能正确回答「什么是线性代数」。

```
能活，但长不高 —— 后半段发育停滞
```

**⇒ 看到 FAIL 不代表模型不可用；
看到 PASS 也不代表模型好。**

这五项指标回答的是「内部表示有没有浪费」，
不是「模型会不会答题」。后者需要评测集。

---

## 2. 实验规模严重不足

本工具的阈值和结论来自：

```
· 1 个模型（自训 3B MoE）
· 1 个提示词（"你好" / "什么是线性代数？"）
· 14 个生成 token
· 单一随机种子（42）
```

**★★ 这不构成任何统计性结论。** 严格地说：

| 想要的结论 | 现在有多少数据 | 需要多少 |
|---|---|---|
| 「残差 ×600 是异常」 | 4 个提示词 | ≥50 个，跨 3 个模型 |
| 「路由卡死 ≥10 = 退化」 | 4 个配置 | ≥30 个配置 × 3 seeds |
| 「E0 是 Super Expert」 | 1 个模型 | ≥3 个开源 MoE 验证 |
| 「两种失效模式」 | 2 个例子 | 需要系统性扫全部 C(8,1..7) |

**★ 如果有读者想引用这些数字，必须先把上表右边的数据补齐。**

---

## 3. 阈值是标定的，不是推导的

`norm_growth ≤ 30`、`stuck_layers ≤ 5` 这些数字**没有理论依据**，
是在一个 3B / 28 层 / 8 专家的模型上「看起来合理」的取值。

**★ 换模型规模时必然需要重新标定。**
相对更稳的两个：

```
max_weight     —— 衡量「head 是否退化为常数」，与规模无关
stuck_layers   —— 衡量「隐藏态是否退化」，与规模关系较弱
```

---

## 4. 指标 ③ 对提示词长度极度敏感

14 个 token 的提示词里，模板标记占了 6 个：

```
<BOS> <用户> \n 什 么 是 线 性 代 数 ？ <TGAI> <回答> \n
 ↑↑↑↑↑↑ 全是结构 token，真正的内容词只有 8 个
```

**⇒ 「内容 head」天然稀少，短提示词会严重低估。**

实测：同一模型，短提示词浅层内容 head = 0 个，
181 token 长提示词浅层 = 4 个。

**★ 建议这一项一律用 100+ token 的真实文本测。**

---

## 5. head 平均会抹平分工

如果用「16 个 head 平均后的注意力」判断模型好坏，会得到错误结论：

```
16 个 head 里：
  8 个死盯 <BOS>（H≈0）
  2 个盯内容词
  6 个平坦无特征
平均之后 → 一个中庸的、接近均匀的分布
→ 看起来"注意力涣散"
```

**★★ 这和「16 个人平均身高看不出谁是篮球运动员」是一个道理。
本工具的所有注意力指标都基于【单个 head】，不做平均。**

---

## 6. 只测最后一个 query 位置

所有注意力指标只取「最后一个 token」的注意力行。

**⇒ 看不到：
  · 其他位置的注意力模式
  · 跨位置的注意力流动（induction / copy 行为）
  · 长距离依赖的结构**

**★ 需要这些时，要把 dump 扩展为多位置采样。**

---

## 7. 路由指标的假设：卡死 = 退化

这个假设在实测中成立（禁 E0 → 卡死 13 层），但**不排除反例**：

```
可能的情况：
  · 某个模型在健康状态下也有若干层固定选同一专家（例如专门处理标点的层）
  · 某些架构（如共享专家 / shared expert）本来就有固定路由
  · 极短的序列里，"8 步都选同一个"可能是正常统计波动
```

**★ 所以「卡死层数」应该看相对变化（训练前 vs 训练中），
而不是绝对值。**

---

## 8. `.tg` 格式与引擎的耦合

本工具依赖：

```
· .tg 文件格式（128 字节头 + 权重索引表 + 权重数据）
· tgai_go 引擎的 dump 机制（c_embed / c_block{i} / c_attn{i} 等文件）
· 引擎导出的 tg_dump_set_enabled / tg_expert_set_disabled
```

**★★ 这些都是 TGAI 项目私有的。其他人要用，必须实现同样的 dump 约定，
或者按 docs/METRICS.md 里的 hook 示例移植。**

**★ 文件头 +112..+127 的 4 个 u32 在 V2.7 里未被写入
（实测 `0, 0, 1, 0xFFFFFEEA`），不能当 arch_type / num_kv_heads 读。
本工具从 `n_experts` 推导架构。**

---

## 9. 已知的 Windows 环境坑

| 坑 | 现象 | 处理 |
|---|---|---|
| **运行时改 `os.environ` 传不进已加载的 DLL** | `TGAI_DUMP_DIR=''` 后仍写文件 | 用引擎的 `tg_dump_set_enabled()`，或进程启动前设好环境变量 |
| **`build.ps1` 会跳过未变更的 .obj** | 改了 .c 但 DLL 哈希不变（仍打印"编译成功"） | 重编前必删 `cpu\build\tgai_engine.obj` |
| **`.NET ReadAllText` 相对路径按进程 CWD 解析** | `[System.IO.File]::ReadAllText('x.py')` 返回 null | PowerShell 里操作文件用绝对路径 |

| 专家消融作为因果审计 | [ICML 2026](https://icml.cc/virtual/2026/79413) |

**★★ 所以：这个项目的定位是「工程工具 + 方法固化」，
不是「科学发现」。请不要把它包装成后者。**

**★ 它可能有的增量：**

```
1. 「卡死层数」作为可直接监控的数值（未在已发表工作中见到）
2. 两种失效模式（卡死 vs 错配）的判别方法
3. 五项指标打包成一个 5 分钟能跑完的脚本
```

**★ 这些增量是否足以支撑一篇论文，需要更大规模的实验才能判断。**

## 11. 使用建议（总结）

```
✅ 适合：
   · 自己训练 MoE 时的中途体检
   · 诊断"输出还能用但内部已退化"的隐性故障
   · 对比两个 checkpoint 的同一个指标

❌ 不适合：
   · 判断模型能不能上线（要用评测集）
   · 跨模型比较绝对分数（阈值需重新标定）
   · 作为论文的核心贡献（增量不足）
```
